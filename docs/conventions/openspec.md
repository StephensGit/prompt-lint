# OpenSpec Workflow

This repo uses OpenSpec for features and non-trivial changes. The `opsx` slash commands and `openspec-*` skills are generated by `openspec init` — don't hand-edit them.

## Directory

```
openspec/
  config.yaml          schema + project context
  specs/               persisted specs
  changes/             one folder per change → archive/ when done
    <change>/
      proposal.md       why + what + impact
      design.md         technical decisions, goals/non-goals, tradeoffs
      tasks.md          numbered implementation checklist
      specs/            scenario-based acceptance criteria
```

## Flow

`/opsx:propose` → proposal → design → specs → tasks → `/opsx:apply` → `/opsx:archive`.

Don't skip artifacts or implement before tasks are written.

## During `/opsx:apply`

- Work the tasks list in order; check off each subtask.
- If you hit a gap or conflict in the design/specs, **stop**, note it in the relevant artifact, and ask — don't silently deviate.
- Post-implementation rules still apply (tests + living-doc updates).

## When to use it

- **Use:** new features, multi-file refactors, anything with real design decisions.
- **Skip:** single-line fixes, typos, config tweaks, or when you've given exact instructions with no decisions to make.
